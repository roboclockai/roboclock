# Galaxea G0.5 (RoboDojo sim checkpoint) in roboclock

`roboclock.envs.lab.policies.g05` drives the dual X5 arms with Galaxea's G0.5 RoboDojo
checkpoint, [`OpenGalaxea/g05-robodojo`](https://huggingface.co/OpenGalaxea/g05-robodojo)
`g05_robodojo_fm_only_checkpoint.tar`. G0.5 is a Qwen3.5-2B-based VLA with a flow-matching
action expert, fine-tuned on the RoboDojo demonstrations (ARX X5, joint actions). It is served by
XPolicyLab's `policy/G05` adapter. For the websocket protocol and the joint mapping shared with
pi0.5, see [xpolicylab-pi05.md](xpolicylab-pi05.md).

## What the checkpoint expects

- **Joint actions, 16 per request.** The model predicts 32 steps of the 14-value RoboDojo joint
  vector `[left j1-6, left gripper, right j1-6, right gripper]`; the adapter returns the first
  16 (`deploy.yml` `action_steps: 16`), and `policy/G05/deploy.py` executes all 16 before it asks
  again. The client does the same.
- **25 Hz.** Each chunk entry is one RoboDojo simulator step, 1/25 s (`env_cfg/arx_x5.yml`
  `collect_freq: 25`). Run `roboclock eval` with `--policy-hz 25`: one act() is one chunk entry,
  ramped over two 50 Hz control steps. The client raises an error at any other rate.
- **`frequency: 30` in `deploy.yml` is not a replay rate.** It is the adapter's fallback for the
  model's control-frequency input when an observation has no `additional_info.frequency`.
  RoboDojo's observation manager always sends its `collect_freq` (25), so the client sends 25.
  G0.5 reads the value only in its AR action tokenizer; this checkpoint decodes actions by flow
  matching. Measured: 25 and 30 give chunks that differ by 0.0023 rad, the same as two samples at
  25 (0.0020 rad).
- **No history, no server-side state.** The checkpoint has `num_obs_steps: 1`, and the
  adapter's `ROBODOJO_G05_OBS_OFFSETS` defaults to `0`, so the `update_obs` calls deploy.py makes
  between chunk entries only replace the observation the next `get_action` reads. The client
  sends one observation per request with the `infer` message (`update_obs` + `get_action` under
  the server's model lock). Episodes may share a server.
- **Observation.** Three JPEG views (`cam_head`, `cam_left_wrist`, `cam_right_wrist`, tagged
  XPL-RGB1, so the server decodes RGB), the six arm joints per arm, and the gripper opening in
  [0, 1]: the last commanded opening clipped to [0, 1], or the measured opening before the first
  command, as RoboDojo reports it. Images are read, and so rendered, only on request frames.

## Setup (policy machine)

```bash
# Weights: the sim checkpoint plus the training base assets, which hold the Qwen3.5 processor.
cd $MODELS_DIR/g05-robodojo
HF_TOKEN=$(cat $HF_TOKEN_FILE) hf download OpenGalaxea/g05-robodojo \
  g05_robodojo_fm_only_checkpoint.tar g05_robodojo_fm_only_checkpoint.tar.sha256 \
  g05_robodojo_train_base_assets.tar g05_robodojo_train_base_assets.tar.sha256 --local-dir .
sha256sum g05_robodojo_fm_only_checkpoint.tar     # fd32a788...ed510, as in the .sha256 file
sha256sum g05_robodojo_train_base_assets.tar      # 188fc8f0...91218
tar -xf g05_robodojo_fm_only_checkpoint.tar && tar -xf g05_robodojo_train_base_assets.tar

# Server venv (uv instead of the adapter's G05_PYTHON + pip; same pins as G05/pyproject.toml).
G=$ROBODOJO_DIR/XPolicyLab/policy/G05
unset TRITON_PTXAS_PATH
uv venv --python 3.10 $G/.venv && export VIRTUAL_ENV=$G/.venv
uv pip install torch==2.7.1 torchvision==0.22.1 torchaudio==2.7.1 --index-url https://download.pytorch.org/whl/cu128
# <deps> = project.dependencies of $G/G05/pyproject.toml without the torch trio.
uv pip install -r <deps> setuptools wheel torch==2.7.1 torchvision==0.22.1 torchaudio==2.7.1 \
  --index-strategy unsafe-best-match --extra-index-url https://download.pytorch.org/whl/cu128 \
  --no-build-isolation-package deepspeed
# The newest flash-attn-4 / quack-kernels need torch >= 2.8; pin a set that runs on torch 2.7.1.
uv pip install flash-attn-4==4.0.0b15 quack-kernels==0.4.1 nvidia-cutlass-dsl==4.5.2
uv pip uninstall nvidia-cutlass-dsl-libs-core nvidia-cutlass-dsl-libs-cu12
uv pip install msgpack msgpack-numpy numpy==1.26.4
uv pip install --no-deps -e $ROBODOJO_DIR/XPolicyLab -e $G/G05
```

The sha256 files name a path on Galaxea's NAS, so `sha256sum -c` fails; compare the hash.
`policy/G05/checkpoints/g05_robodojo_sim` links to `$MODELS_DIR/g05-robodojo`.

Serve:

```bash
bash scripts/xpolicylab/serve_g05.sh $ROBODOJO_DIR 6020 <gpu>
```

The script runs the adapter's own `setup_eval_policy_server.sh` (XPolicyLab's
`setup_policy_server.py` with `policy/G05/deploy.yml`) with `ROBODOJO_G05_ACTION_SOURCE=fm`.

- Loading takes about 3 minutes; each server uses about 13 GB of GPU memory.
- The server never logs a listening line; check the port.
- The first request compiles kernels and takes 40–65 s. Later requests take 0.7–1.0 s on an
  A100 shared with Isaac.

Differences from the published setup:

| Item | Published | Here |
|---|---|---|
| Environment | `uv sync` of `G05/pyproject.toml` (or `pip install` in `G05_PYTHON`) | uv venv with the same pins |
| flash-attn-4 | `>=4.0.0b15`, unpinned | 4.0.0b15 with quack-kernels 0.4.1 and cutlass-dsl 4.5.2: the current 4.0.0b38 + quack 0.6.5 need torch ≥ 2.8 and fail to import on the pinned torch 2.7.1 |
| `G05_HF_PROCESSOR_PATH` | not mentioned in the README | the base assets' `pretrained/hf_processor`; the checkpoint's config requires it and the sim archive has no processor |
| `ROBODOJO_LEROBOT_V30_ROOT` | the training dataset | a placeholder path: the saved config needs a value, serving never reads it |

The first two change at most bf16 rounding; the last two only make the saved config resolve.

## Run (simulator machine)

```bash
export XPOLICYLAB_URL=ws://127.0.0.1:6020 XPOLICYLAB_LOG=qlog/lab_A5_s0.jsonl
PYTHONPATH=src:$ROBODOJO_DIR python -m roboclock eval \
  --env lab --task A5 --difficulty easy --seeds 1 --seed-start 0 \
  --policy roboclock.envs.lab.policies.g05:make --policy-hz 25 \
  --inference-latency zero --output out/lab_A5_s0
```

`XPOLICYLAB_LOG` writes one row per request: server and round-trip time, the gripper state sent
and the gripper commands, clipped targets, and each chunk's start jump and travel.
`G05_FRAME_DIR` keeps the head JPEG of every request; `G05_REPLAN` executes fewer than 16
entries per request.

## Integration check

An open-loop replay of two RoboDojo demonstrations, each frame sent through the client as a
roboclock observation (one act() per 25 Hz frame, so a request every 16 frames), with the
demonstration's gripper state. Every request was also sent twice in RoboDojo's native form
(stored JPEG bytes and stored state). Mean absolute error over the next 16 actions, arm joints
in rad / gripper opening:

| Demo | Requests | roboclock client | native | native noise | client vs native | hold |
|---|---|---|---|---|---|---|
| stack_blocks | 16 | 0.0098 / 0.003 | 0.0091 / 0.003 | 0.0022 | 0.0033 | 0.0912 / 0.086 |
| press_by_number | 23 | 0.0066 / 0.005 | 0.0066 / 0.005 | 0.0017 | 0.0017 | 0.0940 / 0.106 |

The client's error is 7–11% of holding still and matches the native requests within the
model's sampling noise.

An Isaac smoke episode (household A2, seed 0) ran its full 40 s: 63 requests at 25 Hz, every
chunk 16 entries, no clipped arm targets.

## Result: the 30-episode comparison set (2026-11-07)

Setup:

- The 30 episodes used for pi0.5, Wall-X and Qwen: lab A5/B1, hospital A3/B4, household
  A2/B2, sports A3/B2 and industry A1/B2, seeds 0–2, easy (industry too: main has no
  `reviewed_nominal`).
- `--inference-latency zero` and `--policy-hz 25`. Two servers on one A100, two episodes at a
  time, each on its own server.

| | Joint | Physical | Stages reached |
|---|---|---|---|
| G0.5 (this run) | 0/30 | 0/30 | none (every task scores 0) |
| Wall-X (2026-11-06, zero latency) | 0/30 | 0/30 | household A2 `glass_picked_up` 3/3 |
| pi0.5 (2026-11-05, measured latency) | 0/30 | 0/30 | household A2 `glass_picked_up` 3/3 |

What the checkpoint does, from the request log (measured joints and commanded chunks) and the
head frame of every request:

- **It first drives both arms to joint zero.** In all 30 episodes the first one to six chunks
  move the arms from roboclock's start pose to RoboDojo's joint-zero pose with open grippers,
  reached 0.6–4.5 s in (sports B2: 9–13 s). Every RoboDojo demonstration starts and ends at
  joint zero, so this is the checkpoint's learned home pose.
- **In household and hospital it then stays there.** After the first 2 s the arms sit within
  0.15 rad of zero for 68–100% of requests, and the median chunk moves 0.02 rad, with open
  grippers.

| Task | Failure |
|---|---|
| household A2 | Arms at zero for the whole 40 s; the glass is never touched (`time_budget`). |
| household B2 | The arms are at zero by 1.3 s and stay there; the object rolls off the counter at 3–4 s (`object_fell`). |
| hospital A3 | Arms at zero; STOP is never pressed. |
| hospital B4 | Arms at zero; the stopcock is never turned (`time_budget`). |
| lab A5 | The right arm reaches over the bench near the film reel, then the developer times out (`developer_loading_timeout`). |
| lab B1 | The arms reach over the bench, away from the beaker on the hotplate (`overheat`). |
| sports A3 | Arms mostly at zero, one brief reach; the ball is never grasped (`no_grasp`). |
| sports B2 | The arms move during the hold and throw no correct combinations (`moved_during_hold`, `incomplete_combinations`). |
| industry A1 / B2 | The arms reach into the tanks and close the grippers, with no task progress before the time budget. |

Other observations:

- **Server time.** 0.83 s per request at p50 and 1.0 s at p95, over 1810 requests (first request
  of each episode excluded), on an A100 shared with demo-collection Isaac. Under
  `--inference-latency measured` the arms would hold for about 0.8 s after every 0.64 s chunk.
  That run was not made: the zero-latency run already scores 0.
- **Joint limits.** 33 arm targets in 1810 chunks were clipped to the lab limits (industry A1,
  lab B1, sports A3).

Conclusion:

- The open-loop replay reproduces RoboDojo demonstrations within 0.007–0.010 rad (7–11% of
  holding still), and the client's requests match RoboDojo's native ones within the model's
  sampling noise, so the integration is correct.
- In roboclock the checkpoint does less than pi0.5 and Wall-X: in four of the ten tasks it
  returns to its home pose and waits. A run with roboclock's arms started at joint zero would not
  change this, since the policy has no history and reaches that state within 0.6–4.5 s anyway.
